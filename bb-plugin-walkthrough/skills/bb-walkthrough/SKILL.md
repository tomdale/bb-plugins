---
name: bb-walkthrough
description: "Guide a user through a substantial changeset in a BB thread as a conceptual, paused narrative walkthrough, using the Walkthrough plugin's walkthrough_* tools for pause controls, notes, the Walkthrough panel, and PR review drafts. Use for GitHub PR review or local/self/agent-originated work, and whenever a user asks to be walked or guided through changes in BB."
---

Walk through a substantial changeset in teachable conceptual groups. Explain before/after/why, pause between groups, and help the user understand before judging. In BB this skill takes precedence over tdx-walkthrough; use the tdx-narrative skill for baseline style when available. Default: local review. BB renders the controls: the pause form replaces the composer while you wait, the Walkthrough panel shows the outline, per-file diffs, notes, and the review draft, and the plugin mirrors notes to `<session-root>/.agent/review-notes.md`.

Mode: explicit PR intent (PR/GitHub review, feedback, inline comments, PR URL/number) selects PR mode; explicit local/self/agent intent overrides an active PR. Otherwise, before any tutorial text, check whether the checkout has an active PR (`gh pr view --json number,url,title,baseRefName` or `gh pr list --head "$(git branch --show-current)" --state open`); an active PR selects PR mode, and local mode applies only after that check finds none. If still unresolved, ask once: GitHub PR review or local walkthrough? PR mode needs an active checkout PR, a supplied URL/number, or enough metadata to identify one; without it, explain that feedback can be drafted but not attached or posted, and ask the user to choose local mode or confirmed PR mode for a later draft. If this is not a Git repo and no PR, patch, or comparison baseline was supplied, ask for one.

First message: determine mode before printing any introduction. Then say briefly that the walkthrough groups and explains the diff and pauses after each group, where BB's controls let them continue, finish, ask, and record questions and todos (and draft PR comments in PR mode); recorded items appear in the Walkthrough panel and in `.agent/review-notes.md`. Do not print a command table and do not repeat the introduction after pauses or resumes.

Preparation: find the base (normally merge-base with `origin/main` or `origin/master`; in PR mode the PR's base branch), then inspect recent commits, the full `base..HEAD` diff (plus uncommitted changes in local mode), pre-change code (`git show <base>:<path>`), and enough current context to explain accurately. Honor a user-specified range, path, or base; if the base is ambiguous, choose the likely one, state it, and continue.

Start: call walkthrough_start with mode, a short title, baseRef, the PR (number, url, title) in PR mode, and the ordered groups. Name groups by concept, not file; order them by dependency and substance: foundations, API, and data shape before consumers; mechanical follow-ons later; tests with the behavior they cover unless the test strategy merits its own group. Give each group a one-line summary and the workspace-relative locations it explains, with new-side line ranges when known; the panel turns these into file links and diffs, and the pause form offers them as note locations. Set includeUncommitted when the reviewed work is not committed. If the plan stops fitting mid-walkthrough, revise the unpresented groups with walkthrough_update_outline.

Opening: a concise, explanatory, non-evaluative account of prior behavior, the change, its apparent reason, and how the major pieces connect. Mention that notes go to the panel and to `.agent/review-notes.md` once something is recorded, and that the panel's Keep notes file toggle turns the file off. Show the outline with `::walkthrough-outline` on its own line. Then call walkthrough_pause and end your turn; group 1 starts when the user continues.

Groups: when a tool result says to present a group, narrate it: prior behavior, what changed, why, with only relevant snippets and file references; annotate outside snippets unless inline is needed; connect prior groups; do not spoil later groups. Show changed code with `::walkthrough-diff{path="src/file.ts" lines="40-72"}` on its own line (path workspace-relative, lines on the new side), which renders the real hunk against the base; use fenced, language-tagged code for pre-change code or excerpts that are not diff hunks. End each group by calling walkthrough_pause with 3–4 useful questions about the current group as suggestions, then end your turn.

Pausing: walkthrough_pause is always the last action of a message; write nothing after it, because the pause controls are the user's prompt and already offer continue, finish, close, and note recording, so suggestions never repeat those. Every pause result arrives as the walkthrough_pause tool result. Next: present the group it names. Ask: answer short unblocking questions; for tangents suggest recording a question; if the answer depends on a later group, offer to answer now, later, or as a recorded question; then call walkthrough_pause again for the same group, which asks whether to continue. Finish: follow the finish procedure below. Results list notes the user recorded through BB since your last walkthrough call; they are saved already, so do not record them again and do not investigate recorded questions mid-walkthrough. Never automatically record offered questions. If the user dismisses the controls to use chat, wait for their message and call walkthrough_pause when you next stop for input.

Chat input: the user can also steer in chat. Accept the canonical dotted forms and unambiguous natural-language equivalents, otherwise ask once. `.next` and `.finish` map to walkthrough_advance (next, finish). `.question <text>`, `.todo <text>`, `.comment <text>`, and `.note <text>` map to walkthrough_note (kind question, todo, comment, note), attaching the group and current-diff path and line range when known without requiring user syntax; record tersely, preserving intent, briefly confirm kind and locus, and resume. `.notes` means summarize walkthrough_status notes and point to the panel's Notes tab. Record clearly classifiable feedback given in chat the same way; if the kind is unclear, ask whether it is a question, todo, comment, or note. In local mode use comment and note kinds only on explicit request.

Finish: after the last group or on the user's finish, give a brief recap of the sequence and the nonempty notes, then process notes. Local mode: resolve recorded questions from code, diff, tests, and commits with walkthrough_note (status resolved, resolution = the answer) and leave unknowable questions open; then call walkthrough_pause with suggestions offering remaining-question investigation and todo edits or a plan. PR mode, in order: (1) todos: complete or resolve each locally; if one is ambiguous, risky, blocked, or needs user input, stop and ask; resolve completed ones and leave blocked ones open; (2) questions: answer from code, diff, tests, commits, and the PR body, resolving the locally answerable ones and leaving author-intent or unavailable facts open; (3) comments: only now offer a draft review through walkthrough_pause suggestions. When the user accepts, build it with walkthrough_review: unresolved questions become author questions in the body, located comments become inline comments, unlocated comments go in the body; confirm stale, invalid, or ambiguous locations with the user first, then summarize the complete draft, which the panel's Review tab previews. Never offer a GitHub review solely because notes exist. Act on recorded comments or questions only after the user opts in. The user closes the walkthrough with Done in the pause form, or in chat via walkthrough_advance complete.

Posting: never post, submit, or send external review feedback without a separate explicit request. The panel's Post action sends that request into the thread. To post, read the draft with walkthrough_status and submit one review with `gh api repos/{owner}/{repo}/pulls/{number}/reviews` (event, body, and comments with path, line, side, and start_line for ranges), then call walkthrough_review with status posted and the review URL.
