# BB Todo

A BB-native working plan for each thread. The `todo` agent tool owns plan state in the plugin database; the composer card and **Todos** thread panel read and edit that state directly. There is no dependency on Pi's Todo extension, tool-call event replay, or a provider-specific state format. New lists start empty; lists from older Pi Todo threads are not imported.

The `todo` agent tool takes four optional lists and no action names (`agent.ts`):

- `tasks: string[]` replaces the plan with these subjects, numbered 1..n; the first task starts. Replacing a plan that has completed work archives it to `todo_plan_archives`.
- `add: string[]` appends tasks. On an empty plan it behaves like `tasks`.
- `done: number[]` completes tasks.
- `start: number[]` marks pending tasks in progress, for parallel or resumed work.

Operations apply in that order. When a call completes a task or adds one and leaves nothing in progress, the first pending task without unfinished blockers starts. Unknown ids are reported while the rest of the call applies. A call with no arguments only reads. Every result is the current plan, one line per task (`✓` completed, `▶` in progress, `○` pending, with unfinished blockers noted). Models often send `""`, `[]`, `{}` or `null` for fields they do not mean, so blank values count as absent and a bare item is accepted as a one-item list. Fields outside the four are rejected before anything applies.

Subtasks, `blockedBy`, owners, descriptions, and metadata exist in the data model and the Todos panel, not in the agent tool. Panel edits and agent calls go through the same reducer (`model.ts`).

The UI has three surfaces. The composer card sits above the prompt, or becomes a gutter lane when the thread's left gutter fits. The lane is vertically centered in the thread beside the conversation, and stays in the gutter even while no message is on screen. It is frameless and always shows the full list (labels wrap), with no count, collapse, or edit controls; a persistent **Todos** button with a list icon sits above the list and opens the Todos panel; the icon and label are one target. Below the width where the gutter fits, and in queued-message composers, the card stays above the prompt. As a composer banner, when collapsed, it shows in-progress tasks, 'X of Y todos done' with a progress circle when none are in progress, or 'All todos complete' when all tasks are complete; clicking anywhere on the collapsed card expands it to the full list. Expanding shows the full list with subtasks grouped under their parent and rendered in 2 balanced columns when the card is wide, with scroll fade gradients when overflowing, and clicking anywhere non-interactive collapses it back. The **Todos** panel edits the list: a status menu per task that disables transitions the reducer rejects, inline subjects, a details disclosure for description, working label, owner and blockers, and a row menu for moving, nesting and deleting. On a subject field, Alt+Up/Down reorders siblings and Cmd+] / Cmd+[ (Ctrl elsewhere) nests under the previous sibling or moves out of the parent. Controls under `components/ui/` are vendored from BB's shadcn registry (`components.json`).

State belongs to its BB thread and persists across provider sessions and plugin reloads. A thread becoming idle, failed, or archived settles every unfinished `in_progress` task back to `pending`; the next `done` starts the following task, and `start` marks resumed work. Deleting a thread removes its task state. The composer card shows progress and announces unfinished blockers to screen readers (rows do not draw them); an all-complete card hides after 30 seconds by default (`completedHideDelaySeconds` controls the delay).

Run `npm ci`, `npm run typecheck`, `npm test`, and `npm run build` from this directory. The repository's `scripts/bb-plugin-smoke` checks activation in a throwaway BB server. The daily app loads the plugin from the canonical `main/bb-plugin-todo` path, not a task checkout.
